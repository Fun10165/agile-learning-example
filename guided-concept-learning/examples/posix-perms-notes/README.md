# POSIX 权限系统 · 敏捷学习笔记

## 知识范围

按这些假定来写；哪条与你不符，直接指出，以纠正为准：

- 你熟悉文件系统的基本行为：文件里放内容，目录里放文件（和别的目录）。
- 你知道一台机器可以同时有多个用户，用户可以被编进组。
- 对权限系统本身不需要任何使用经验——本版从它最初的问题讲起。

目标：讲清权限系统的判定规则——它由哪些需求逼出来、怎么算。

## 动机

一台机器上有多个用户，共享同一棵目录树，需要一条简单规则回答：**谁，能对这个文件做什么？**

规则要足够便宜：每个文件只能花几个字节记录权限，每次判定只做几次比较。这个约束决定了表达方式：用固定大小的位图，把「身份 × 操作」编码成几个开关。身份按与文件的关系取最常见三档——文件的主人、主人所在的圈子、其余人；操作取三种——读取、写入、执行。

位图能覆盖常规的访问控制，但有两类现实矛盾它管不住：

- 公共目录（`/tmp`）人人可写。写入位本身就允许删除条目，于是人人可写就成了人人可删，用户之间可以互相破坏。
- 普通用户可以修改自己的密码，而密码数据只有 root 能写。按位图，普通用户碰不到那些数据。

两类矛盾各需要一个附加的开关，加在模式位里。这就是三个特殊位的来历。

## 模型

每个文件带三样记号：一个属主（owner）、一个组（group）、一组模式位。模式位共 12 个：9 个权限位定义基本访问规则，3 个特殊位修改其中几条规则的语义。

### 基本规则：三类身份 × 三种操作

- 三类身份：属主（owner）、与属主同组的用户（group）、其他用户（others）。
- 三种操作：读取（r）、写入（w）、执行（x）。

同样是 rwx 三位，用在常规文件与目录上时含义不同：

| 位 | 常规文件 | 目录 |
|---|---|---|
| r | 读取文件内容 | 列出目录中的条目名称 |
| w | 修改文件内容 | 在目录中创建、删除、重命名条目 |
| x | 执行该文件 | 进入或穿越该目录 |

### 三个特殊位

**sticky**，用在目录上。它只给「删除与重命名」附加条件，其余操作一概不碰。为什么恰好是这两个操作？把三件事分开看，再对照 `/tmp` 的需求，答案就清楚了。

三件事的分工：

- **目录的写入位**：管条目层面的操作——创建、删除、重命名目录中的条目；
- **文件自身的权限位**：管文件内容的读写——新建文件一般是 `644`，别人可读不可写；
- **sticky**：只修正上面第一条里的「删除与重命名」这一部分。

`/tmp` 的三项需求：

1. 人人能创建自己的文件 → 目录写入位必须开放，创建不受限；
2. 文件内容不被别人改写 → 由各自的权限位负责（`644` 时别人改不了），不需要目录层介入；
3. 文件不被别人删掉或改名 → 没有现成机制可用：删除与重命名由父目录的写入位唯一决定，与文件自身权限无关；人人可写必然带来人人可删。

需求 1、2 都能用已有机制表达，需求 3 不能——sticky 补的就是这个洞。

机制：目录带 sticky 时，删除或重命名其中的条目，额外要求操作者是该条目的属主，或该目录的属主（特权用户不受此限，原因见缺口清单）。典型用例 `/tmp`：`drwxrwxrwt`，人人可写，互不删除。

**setuid**，用在可执行文件上：运行时以文件属主的身份运行。典型用例是 `/usr/bin/passwd`：属主是 root，普通用户通过它改写自己的密码。

**setgid**，在两种对象上行为不同：

- 可执行文件：运行时以文件所属组的身份运行；
- 目录：其中新建条目的组取该目录的组——共享目录的常用手法，`chmod g+s` 之后，成员们新建的文件自动属于共享组。

### 读法与写法

`ls -l` 的第一列给出类型与模式位：类型一位（`-` 常规文件，`d` 目录，`l` 符号链接），随后九位按身份分三组；特殊位与各自组内的执行位共用显示字符。

```
-rw-r--r--   普通文件：属主可读写，同组可读，其他可读
drwxr-x---   目录：属主可读写与穿越，同组可读与穿越，其他无权
-rwsr-xr-x   属主位显示 s：setuid，且属主的执行位已设置
-rwSr--r--   属主位显示 S：setuid，但属主的执行位未设置
-rwxr-sr-x   组位显示 s：setgid，且组的执行位已设置
drwxrwxrwt   其他位显示 t：sticky，且其他的执行位已设置
drwxrwx--T   其他位显示 T：sticky，但其他的执行位未设置
```

规则：执行位已设置时显示小写字母（`s`、`t`），未设置时显示大写字母（`S`、`T`）。

模式位写成八进制时，特殊位占第四位数字：`644`（`rw-r--r--`）、`750`（`rwxr-x---`）、`4755`（`rwsr-xr-x`，4 是 setuid）、`1777`（`rwxrwxrwt`，1 是 sticky）。

一个例子：

```
$ ls -l report.txt
-rw-r-----  1 alice dev  1024  report.txt
```

属主 alice 可以读取与修改；`dev` 组的成员可以读取；其余用户没有任何权限。这个文件的模式写成八进制是 `640`。

## 缺口清单

每个缺口标注类型，类型决定「解决它要做什么」：

- **内在矛盾**：已写下的规则在某个场景产生与需求冲突的行为（解决它要调和规则，或补一个补偿机制）；
- **未 spec 清楚**：机制在现实中已存在，模型文本尚未覆盖（解决它是补描述）；
- **扩展需求**：模型表达不了的、被需要的新能力（解决它是加结构）。

本版故意留下的不明确处：

1. **进程的身份**（未 spec 清楚）：setuid 说「运行时以文件属主的身份运行」——这个「身份」是进程里的什么？访问发生时，依据什么把访问者归入「属主 / 同组 / 其他」？
2. **多组归属**（未 spec 清楚）：一个用户同时在多个组里时，算不算「同组」？
3. **特权用户**（未 spec 清楚）：超级用户（root）不受这些位约束，为什么？
4. **目录位的来历**（未 spec 清楚）：目录的执行位含义与文件不同，这个设计从哪里来？（猜想：与路径逐级穿越有关）
5. **创建时的权限**（未 spec 清楚）：新建文件的权限从哪来？setgid 目录的「继承组」说明创建时刻还有别的规则在起作用。
6. **更细的规则**（扩展需求）：只有三类身份时，能不能表达比 owner / group / others 更细的控制？
7. **特殊位的边界**（未 spec 清楚）：脚本上的 setuid 为什么不生效？`nosuid` 挂载选项（实践里常见）为什么会忽略这些位？

这些缺口就是后续每一版的动机来源：每版挑一个缺口，引入回答它所需的最小机制。

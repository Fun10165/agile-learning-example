# POSIX 权限系统 · 敏捷学习笔记

## 知识范围

按这些假定来写；哪条与你不符，直接指出，以纠正为准：

- 你熟悉文件系统的基本行为：文件里放内容，目录里放文件（和别的目录）。
- 你知道一台机器可以同时有多个用户，用户可以被编进组。
- 对权限系统本身不需要任何使用经验——本版从它最初的问题讲起。

目标：讲清权限系统的判定规则——它由哪些需求逼出来、怎么算。

## 动机

一台机器上有多个用户，共享同一棵目录树，需要一条简单规则回答：**谁，能对这个文件做什么？**

规则要足够便宜：每个文件只能花几个字节记录权限，每次判定只做几次比较。这个约束决定了表达方式：用固定大小的位图，把「身份 × 操作」编码成几个开关。身份按与文件的关系取最常见三档——文件的主人、主人所在的圈子、其余人；操作取三种——读取、写入、执行。

三类身份里的「组」还有一条现实补充：一个人可以同时属于多个组（比如同时参与几个项目，各有一个组），而文件的模式位里只有一栏组。「同组」的判定因此必须把用户的全部组都算进来，只认某一个就会让「按组授权」在成员跨组的现实下失灵。

位图里还有一个问题值得追到底：目录的 x 位为什么表示「穿越」？答案与路径有关——文件总是以路径形式被访问（哪怕只是当前目录下的一个名字，也要经过当前目录这一级），每经过一级，都需要一次「能不能通过」的判定，x 位就是这个判定。

前面几版一直借用「用户」与「身份」这两个词说话，现在把它定义清楚：判定的一方是进程——每个进程携带一组身份字段，访问文件时，判定用的就是这些字段。为什么是一组？因为「谁启动的」与「当前以谁的名义运行」可以是两个不同的值——setuid 的全部意义就藏在这个差别里。

位图能覆盖常规的访问控制，但有两类现实矛盾它管不住：

- 公共目录（`/tmp`）人人可写。写入位本身就允许删除条目，于是人人可写就成了人人可删，用户之间可以互相破坏。
- 普通用户可以修改自己的密码，而密码数据只有 root 能写。按位图，普通用户碰不到那些数据。

两类矛盾各需要一个附加的开关，加在模式位里。这就是三个特殊位的来历。

## 模型

判定涉及两侧。文件一侧：每个文件带一个属主（owner）、一个组（group）、一组模式位（共 12 个：9 个权限位定义基本访问规则，3 个特殊位修改其中几条规则的语义）。进程一侧：每个进程携带一组身份字段。

### 进程的身份

每个进程携带一组身份字段：

| 字段 | 含义 |
|---|---|
| real uid / gid | 启动这个进程的用户（判定不使用它） |
| effective uid / gid | 当前生效的身份（**判定使用它**） |
| saved set-user-ID / set-group-ID | exec 后生效身份的副本；setuid 程序借它在「提权身份」与「real 身份」之间切换 |

除此之外，进程还携带一个附加组列表；判定「同组」时用 effective gid 加上这个列表。

身份从哪来：登录时会话进程建立初始身份；fork 出的子进程复制父进程的身份；exec 时按「特殊位」一节的规则决定是否替换 effective 一侧（没有特殊位时原样保留）。

日常说法「bob 能不能读这个文件」，完整的说法是「bob 启动的进程能不能读」——判定比对的是进程的 effective 身份与文件的元数据。

### 判定规则：三个类别 × 三种操作

- 三个类别：属主（owner）、文件所属组的成员（group）、其他用户（others）。
- 三种操作：读取（r）、写入（w）、执行（x）。

归类按顺序进行，命中即停：

1. 进程的 effective uid 与文件的属主相同 → 属主类别；
2. 否则，文件的组落在进程的组身份集合里 → 组成员类别；
3. 否则 → 其他类别。

命中之后只用该类别的三位，彼此不叠加——属主即使在组里，也只用属主的三位。

关于组类别有一个要点：**进程的组身份不止一个**——effective gid，加上若干附加组（来自启动进程的用户的组信息，`id` 的输出能看到全部）。文件的组只要匹配其中任意一个，就算同组。

这里有一处不对称值得记住：文件侧只有一个组槽位，进程侧可以有很多组；判定就是拿文件的那一个组，去对进程的整组身份。

同样是 rwx 三位，用在常规文件与目录上时含义不同：

| 位 | 常规文件 | 目录 |
|---|---|---|
| r | 读取文件内容 | 列出目录中的条目名称 |
| w | 修改文件内容 | 在目录中创建、删除、重命名条目 |
| x | 执行该文件 | 进入或穿越该目录 |

目录的 x 位在**路径解析**中被检查。所谓路径解析，就是内核把 `/srv/share/doc.txt` 这样的路径逐级展开（`/srv` → `/srv/share` → 目标）的过程，每一级都要求 x——**路径上任何一级缺 x，目标就够不到**；够到以后，再按目标自己的位判定。

r 与 x 在目录上管着两件独立的事，可以分开观察：

- 只有 r 没有 x：能列出目录里的名字，但读不到条目的属性，也打不开里面的文件；
- 只有 x 没有 r：列不出名字，但知道确切名字就能访问它。

相关：`cd` 进入目录需要 x（不需要 r）；`ls -l` 需要 r 与 x 两者（先列名字，再逐条读属性）。

### 三个特殊位

**sticky**，用在目录上。它只给「删除与重命名」附加条件，其余操作一概不碰。为什么恰好是这两个操作？把三件事分开看，再对照 `/tmp` 的需求，答案就清楚了。

三件事的分工：

- **目录的写入位**：管条目层面的操作——创建、删除、重命名目录中的条目；
- **文件自身的权限位**：管文件内容的读写——新建文件一般是 `644`，别人可读不可写；
- **sticky**：只修正上面第一条里的「删除与重命名」这一部分。

`/tmp` 的三项需求：

1. 人人能创建自己的文件 → 目录写入位必须开放，创建不受限；
2. 文件内容不被别人改写 → 由各自的权限位负责（`644` 时别人改不了），不需要目录层介入；
3. 文件不被别人删掉或改名 → 没有现成机制可用：删除与重命名由父目录的写入位唯一决定，与文件自身权限无关；人人可写必然带来人人可删。

需求 1、2 都能用已有机制表达，需求 3 不能——sticky 补的就是这个洞。

机制：目录带 sticky 时，删除或重命名其中的条目，额外要求操作者是该条目的属主，或该目录的属主（特权用户不受此限，原因见缺口清单）。典型用例 `/tmp`：`drwxrwxrwt`，人人可写，互不删除。

**setuid**，用在可执行文件上：exec 时把进程的 effective uid 替换为文件属主（real uid 保持不动）。典型用例是 `/usr/bin/passwd`：属主是 root，普通用户通过它改写自己的密码。

**setgid**，在两种对象上行为不同：

- 可执行文件：exec 时把 effective gid 替换为文件所属组；
- 目录：其中新建条目的组取该目录的组——共享目录的常用手法，`chmod g+s` 之后，成员们新建的文件自动属于共享组。

### 读法与写法

`ls -l` 的第一列给出类型与模式位：类型一位（`-` 常规文件，`d` 目录，`l` 符号链接），随后九位按身份分三组；特殊位与各自组内的执行位共用显示字符。

```
-rw-r--r--   普通文件：属主可读写，同组可读，其他可读
drwxr-x---   目录：属主可读写与穿越，同组可读与穿越，其他无权
-rwsr-xr-x   属主位显示 s：setuid，且属主的执行位已设置
-rwSr--r--   属主位显示 S：setuid，但属主的执行位未设置
-rwxr-sr-x   组位显示 s：setgid，且组的执行位已设置
drwxrwxrwt   其他位显示 t：sticky，且其他的执行位已设置
drwxrwx--T   其他位显示 T：sticky，但其他的执行位未设置
```

规则：执行位已设置时显示小写字母（`s`、`t`），未设置时显示大写字母（`S`、`T`）。

模式位写成八进制时，特殊位占第四位数字：`644`（`rw-r--r--`）、`750`（`rwxr-x---`）、`4755`（`rwsr-xr-x`，4 是 setuid）、`1777`（`rwxrwxrwt`，1 是 sticky）。

一个例子：

```
$ ls -l report.txt
-rw-r-----  1 alice dev  1024  report.txt
```

属主 alice 可以读取与修改；`dev` 组的成员可以读取；其余用户没有任何权限。这个文件的模式写成八进制是 `640`。

再看一个「组身份」的判定：

```
$ id bob
uid=1001(bob) gid=1001(bob) groups=1001(bob),2000(dev)
```

bob 的主组是 `bob`，但他同时是 `dev` 组的成员（附加组）。`report.txt` 的组是 `dev`，落在 bob 的组身份集合里，所以 bob 可以读取它。

## 缺口清单

每个缺口标注类型，类型决定「解决它要做什么」：

- **内在矛盾**：已写下的规则在某个场景产生与需求冲突的行为（解决它要调和规则，或补一个补偿机制）；
- **未 spec 清楚**：机制在现实中已存在，模型文本尚未覆盖（解决它是补描述）；
- **扩展需求**：模型表达不了的、被需要的新能力（解决它是加结构）。

本版故意留下的不明确处：

1. **特权用户**（未 spec 清楚）：超级用户（root）不受这些位约束，为什么？
2. **创建时的权限**（未 spec 清楚）：新建文件的权限从哪来？setgid 目录的「继承组」说明创建时刻还有别的规则在起作用。
3. **更细的规则**（扩展需求）：只有三个类别时，能不能表达比 owner / group / others 更细的控制？尤其：文件只有一个组槽位，无法同时给两个组授权。
4. **特殊位的边界**（未 spec 清楚）：脚本上的 setuid 为什么不生效？`nosuid` 挂载选项（实践里常见）为什么会忽略这些位？
5. **链接与路径**（未 spec 清楚）：符号链接与硬链接如何参与路径解析与判定？符号链接自身的权限位为什么不参与判定？
6. **身份切换**（未 spec 清楚）：进程怎样切换自己的身份（setuid 家族调用）？saved 字段的完整规则是什么？
7. **判定的时刻**（未 spec 清楚）：判定发生在哪一刻？已经打开的句柄在权限被改动后还受约束吗？

这些缺口就是后续每一版的动机来源：每版挑一个缺口，引入回答它所需的最小机制。

## 概念覆盖审计

本版出现的概念 → 定义位置：

- 属主（owner）、组（group）、其他用户（others） → 「模型 · 判定规则」
- 主组 / 附加组（组身份） → 「模型 · 进程的身份」与「判定规则」
- 进程与身份字段（real / effective / saved uid / gid） → 「模型 · 进程的身份」
- 权限位（九位）与特殊位（共 12 位模式位） → 「模型」开头与「三个特殊位」
- sticky / setuid / setgid → 「三个特殊位」
- 位图、模式位 → 「动机」
- 读法与写法：`s` / `S` / `t` / `T`、八进制第四位 → 「读法与写法」
- 路径解析与目录 x 位（逐级穿越） → 「模型 · 判定规则」

只出现名字、本版还没覆盖：特权用户（缺口清单第 1 条）。

按假定已知、不定义：文件、目录、用户、组、目录树、命令 `chmod` / `ls` / `id` / `cd`。
